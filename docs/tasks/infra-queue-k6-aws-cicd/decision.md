## 구현 결정 사항

### 인프라 범위를 네 가지로 한정한다
- 결정: 작업 큐 · k6 · AWS · CI/CD만 한다.
- 이유: 인턴 경험(실시간 데이터·저장 정합성·동시성·운영 안정성)과 겹치지 않으면서 비어 있던 칸(비동기 처리, 부하 테스트 수치, 클라우드)을 채운다. 나머지는 설계와 충돌하거나 효용이 작다.
- 검토한 대안:
  - decimal 금액 연산: 1초 목표와 충돌, 효용 작음 → 제외
  - ECOS 매일 배치 수집: 재현성(NFR-02)과 보정 검증을 깨뜨림 → 제외
  - 입력 스냅샷 저장(감사 추적): NFR-06 위반 → 제외
  - 민감 필드 암호화·낙관적 락: 서버에 사용자 데이터가 없어 적용 대상 없음 → 제외

### 큐는 `/robust`에만 적용한다
- 결정: 나머지 계산 API는 동기 유지.
- 이유: `/simulate` 등은 엔진 단독 0.1~1.1초로 NFR-03(1초·3초) 안. 큐를 거치면 오히려 지연과 폴링이 늘어난다.
- 검토한 대안:
  - 모든 계산 API를 큐로: 응답 목표가 짧은 API에 불필요한 복잡도 → 기각

### 큐·결과 저장소는 Redis로 한다 (잠정)
- 결정: Redis (ElastiCache) 하나로 큐와 결과(TTL 10분)를 함께 처리한다.
- 이유: 결과를 TTL로 자동 삭제하는 것까지 한 곳에서 해결된다.
- 검토한 대안:
  - SQS + 별도 결과 저장소: 관리형이라 안정적이지만 저장소가 둘이 됨 → 보류
  - DB 테이블 큐 (`SELECT … FOR UPDATE SKIP LOCKED`): RDB 락 경험이 생기지만, 입력을 보관하지 않는 구조에 DB를 새로 들이는 셈 → 보류
- 재검토 조건: 팀이 SQS를 선호하거나 DB를 다른 이유로 두게 되면 다시 검토

### 경로 수를 늘려 부하를 만들지 않는다
- 결정: 부하 테스트는 동시 사용자 수와 `/robust` 동시 작업 수로 만든다.
- 이유: 경로 수를 바꾸면 보고서 7.10 수렴 검증과 어긋난다.

### CI는 PR마다 테스트 + 이미지 빌드 + 컨테이너 헬스체크 (2026-11-10)
- 결정: `ci.yml`에서 `./gradlew test`(정답 파일 대조 포함) → Docker 이미지 빌드 → 컨테이너를 띄워 `/actuator/health` 확인. 같은 브랜치의 이전 실행은 취소.
- 이유: 배포에 쓰는 Dockerfile을 PR 단계에서 그대로 검증해야 "테스트는 통과했는데 이미지가 안 뜨는" 경우를 막는다 (실제로 로컬 JDK 경로가 든 `gradle.properties` 때문에 이미지 빌드가 깨진 적이 있다, c61d0cd).
- 헬스체크는 업무 API(`/api/meta`) 대신 actuator `health`만 연다. 다른 actuator 엔드포인트는 닫는다.

### 무료 Render가 느린 원인은 CPU다 (2026-11-10)
- 측정: k6, 사용자 1명 × 10회, S1 입력 (`perf/k6/api-latency.js`, Perf 워크플로)

| API | 목표 | 로컬 중앙값 (8코어) | Render 무료 중앙값 / p95 | 배율 |
|---|---|---|---|---|
| `/simulate` | 1초 | 0.02초 | 1.45초 / 2.10초 | 약 70배 |
| `/simulate/preview` | 1초 | 0.03초 | 2.65초 / 3.06초 | 약 90배 |
| `/compare` (계획 3개) | 3초 | 0.05초 | 4.39초 / 4.70초 | 약 90배 |
| `/reverse` | 3초 | 0.13초 | 12.41초 / 13.41초 | 약 95배 |
| `/allocations/recommend` | - | 0.34초 | 31.91초 / 32.43초 | 약 94배 |

- 판단: 모든 API가 같은 비율로 느리다 → 특정 코드 문제가 아니라 계산량 × CPU 문제. 엔진은 경로 2,000개를 `parallel()`로 나눠 계산하는데(`SimulationEngine.java:65`), 로컬 8코어 대비 Render 무료는 CPU 0.1개라 이론상 약 80배. 측정 배율과 맞는다.
- 첫 회차는 중앙값 0.75초, p95 6.83초로 들쭉날쭉했다. 공유 CPU라 순간 여유가 있었던 것으로 추정. 두 번째 회차가 실제 수준.
- 측정 도구 버그: 주소가 `/`로 끝나 첫 요청이 `//api/meta`로 갔다. 끝 `/`를 떼고 200일 때만 시간을 기록하도록 고쳤다.
- 경로 수를 줄이는 방법은 쓰지 않는다 (위 "경로 수를 늘려 부하를 만들지 않는다"와 같은 이유, 보고서 7.10).

### 배포 대상을 Render에서 EC2 한 대로 바꾼다 (2026-11-10)
- 결정: EC2 t3.small(2 vCPU, 2GB) 한 대에 Docker로 실행.
- 이유: CPU가 0.1 → 2개로 약 20배. 위 배율이면 `/reverse`가 1초 안팎으로 목표 안에 들어올 것으로 본다 (측정으로 확인 필요). 무료 플랜 크레딧($140, 2027-05-10까지) 안에서 월 약 $20 수준.
- 검토한 대안:
  - Render 유료 플랜: 가장 쉽지만 배포 경로를 직접 구성하는 부분이 적다 → 보류
  - ECS Fargate + ALB (원래 계획): 월 $60 이상, 서버 한 대 규모에 과함 → 보류. 작업 큐·워커 분리 때 다시 검토
  - t3.micro: 메모리 1GB라 Docker + JVM에 부족 → 기각
  - t4g.small(ARM): 더 싸고 2026년 말까지 무료지만, 이미 만든 x86 인스턴스에서 바꿀 수 없고 ARM 이미지 빌드가 필요 → 나중에 바꿀 수 있게 `platforms` 한 줄로 분리
- 리전은 시드니(ap-southeast-2). 무료 플랜 계정은 처음 정해진 리전만 쓸 수 있다. 한국에서 요청마다 약 0.13~0.15초 늘지만 계산 시간에 비해 작다. 유료 전환은 크레딧 소진 후 실제 과금이라 하지 않는다.

### 접근 제어: 저장된 키 없이 OIDC, SSH 대신 SSM (2026-11-10)
- 결정:
  - GitHub Actions는 OIDC로 IAM 역할 `github-actions-deploy`의 임시 자격 증명을 받는다. 신뢰 조건은 `repo:Financial-Simulation/capstone-backend:environment:production`.
  - 권한은 ECR `capstone-backend` 푸시 + 이름 태그 `capstone-backend`인 인스턴스에 `AWS-RunShellScript` 실행 + 결과 조회만 (`infra/aws/`).
  - 서버에는 SSM으로 명령을 보낸다. 보안 그룹에 22번 포트가 없고 키 페어도 없다.
- 이유: 오래 사는 액세스 키나 SSH 키를 GitHub에 두면 유출 시 범위가 크다. 작업마다 발급되는 토큰은 수명이 짧고, 조건으로 레포·환경을 묶을 수 있다. SSM 명령은 AWS에 기록이 남는다.
- 검토한 대안:
  - IAM 사용자 액세스 키를 GitHub Secrets에: 가장 간단하지만 키 교체·유출 관리 부담 → 기각
  - SSH 배포(키를 Secrets에, 22번 개방): 포트 노출 + 키 관리 → 기각
  - 신뢰 조건을 `ref:refs/heads/main`으로: 배포 작업이 `environment`를 쓰면 토큰의 `sub`가 환경 기준으로 바뀌어 맞지 않는다. 환경 기준이 범위도 더 좁다 → 환경 기준으로
  - 정책에 인스턴스 ID를 직접 적기: 인스턴스를 다시 만들 때마다 정책 수정 → 이름 태그 조건으로

### 증적과 롤백 (2026-11-10)
- 결정:
  - 이미지 태그는 커밋 SHA 12자리, ECR 태그 변경 불가(Immutable). 같은 SHA 이미지가 있으면 빌드를 건너뛰고 배포만 한다.
  - 서버 스크립트(`scripts/deploy/ec2-deploy.sh`)가 교체 전 이미지를 기록하고, 새 컨테이너가 120초 안에 헬스체크를 통과하지 못하면 이전 이미지로 되돌린다. 이력은 `/opt/capstone/deploy-history.log`.
  - 수동 롤백은 Deploy 워크플로를 예전 SHA로 실행.
  - 실행 요약에 커밋 · 이미지 · 실행자 · SSM 명령 ID · 시각을 남긴다.
- 이유: "언제 어떤 커밋이 누구에 의해 나갔고, 실패하면 무엇으로 돌아갔나"를 사람이 기억하지 않아도 남게 한다.
- 검토한 대안:
  - `latest` 태그로 배포: 무엇이 돌고 있는지 알 수 없고 롤백 대상이 사라짐 → 기각
  - 롤백을 GitHub Actions에서 따로 실행: 서버 안에서 바로 되돌리는 쪽이 단계가 적고 네트워크 실패에 덜 민감 → 서버 스크립트에서
