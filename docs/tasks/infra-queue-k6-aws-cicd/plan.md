# 계획 (Plan)

> 작업명: 인프라 — 작업 큐 · k6 부하 테스트 · AWS 배포 · CI/CD
> 최종 업데이트: 2026-10-10
> 상태: **팀 합의 전**. 보고서 4장(시스템 구조)·8.3(일정)에도 반영 필요

## 목표

캡스톤에서 **비동기 처리·부하 테스트 실측 수치·클라우드 배포**를 채운다.
범위는 네 가지로 한정한다: 작업 큐, k6, AWS, CI/CD.

## 지킬 원칙

- 경로 수·기간은 보고서 기준 유지 (2,000경로 × 120개월). 부하를 키우려고 늘리지 않는다 (보고서 7.10)
- 서버는 입력을 보관하지 않는다 (NFR-06). 큐에 잠깐 들어가는 입력도 예외가 아니다
- `/simulate`·`/compare`·`/reverse`는 동기 유지 (NFR-03: 1초·3초). 큐는 `/robust`에만 적용

## 1. 작업 큐 (`/robust`)

- 구조: `POST /api/robust` → 큐에 작업 등록 → 워커가 꺼내 계산 → 결과 저장 → `GET /api/robust/{jobId}`로 조회
- 큐·결과 저장소: Redis (ElastiCache). 결과는 TTL 10분, 지나면 `JOB404`
- 작업 상태: `QUEUED` → `RUNNING` → `DONE` / `FAILED`
- 큐 메시지 안의 입력은 워커가 꺼내는 즉시 삭제, 메시지 TTL도 짧게. 결과에는 숫자만 남긴다 (NFR-06)
- 같은 입력 중복 방지: 입력 해시 + seed로 진행 중인 작업이 있으면 같은 `jobId` 반환 (해시만 키로, 입력 원문은 저장하지 않음)
- 실패 시 재시도 1회, 그래도 실패하면 `FAILED`
- 대기열 길이 상한을 넘으면 `JOB4001`
- 워커는 API 서버와 분리해 수평 확장 → 기존 '단일 인스턴스 전제' 삭제

## 2. k6 부하 테스트

- 목표 (NFR-03 기준)
  - `/simulate` p95 1초 이내
  - `/compare`(계획 3개)·`/reverse` p95 3초 이내
  - `/robust` 작업 완료까지 시간, 동시 작업 수별 처리량
- 시나리오: 동시 사용자 단계별 증가 (예: 10 → 50 → 100), S1~S3 예시 입력 사용

## 3. AWS 배포

- API 서버·워커: 컨테이너로 ECS 또는 EC2
- Redis: ElastiCache
- 헬스체크 엔드포인트, 환경변수·비밀값은 코드에 넣지 않고 관리 (Secrets Manager 또는 Parameter Store)
- `params.json`은 이미지에 포함 (배포 전 고정, 실행 중 바뀌지 않음)

## 4. CI/CD (GitHub Actions)

- 순서: 테스트 → 이미지 빌드 → ECR 푸시 → 배포 → 헬스체크 확인 → 실패 시 롤백
- 테스트 단계에 **파이썬 기준 구현 정답 파일 대조** 포함 (확정 계산 오차 1e−6 이하, 확률은 오차 3배 이내, 보고서 8.3)

decimal 연산, ECOS 배치 수집, 입력 스냅샷 저장, 민감 필드 암호화, 낙관적 락 → 이유는 [[../api-spec-revamp/decision|API 개편 결정 노트]]
