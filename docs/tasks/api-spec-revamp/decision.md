# 결정 노트 (Decision)

> 최종 업데이트: 2026-10-21
> 상태: 노션 명세 반영 완료 (2026-10-08). 구현 진행 중

## 작업 경계

노션 「선빈 api 명세서」를 설계 보고서(2026-10-07)와 계산 엔진 v1.6에 맞게 고친다.

- 엔드포인트 **32개 → 12개** (전체 목록은 [[../../architecture/api-overview|API 구조 개요]])

**범위 밖**: 실제 구현, 보고서 수정(별도로 보고서 담당이 고침), 인프라([[../infra-queue-k6-aws-cicd/plan|인프라 작업]])

## 구현 결정 사항

### 사용자 입력을 서버에 저장하지 않는다
- 결정: 입력은 브라우저 localStorage(`simInput.v1`)에 두고, 계산 API가 매번 본문 `input`으로 받는다. profileId·`X-Profile-Id` 헤더·저장 API 전부 삭제.
- 이유: 보고서 NFR-06("입력값을 서버에 저장하지 않음")과 기존 명세(프로필·목표·시나리오·이벤트 DB 저장)가 정면 충돌. 저장하면 로그인·권한·암호화까지 따라와 범위가 커진다.
- 대가: 다른 기기에서 이어서 하기 불가, 브라우저 데이터를 지우면 입력이 사라짐, 요청 본문이 커짐.
- 검토한 대안:
  - 프로필 DB 저장 + UUID 식별 (기존 명세): NFR-06 위반으로 기각
  - 입력 스냅샷만 저장 (감사 추적용): 역시 NFR-06 위반으로 기각. 재현성은 아래 seed 방식으로 확보

### 재현성은 seed + startMonth로 보장한다
- 결정: 응답에 `seed`·`modelVersion`을 항상 넣고, 기준 달은 입력의 `startMonth`를 쓴다. seed 기본 `20261007`.
- 이유: 입력은 사용자 브라우저에 있으니 같은 입력 + seed면 언제든 같은 결과가 나온다. 서버 날짜를 쓰면 다음 달에 같은 입력의 결과가 바뀐다 (NFR-02 위반).
- 대가: 몇 달 뒤 이어서 하면 과거 기준으로 계산됨 → 프론트가 "기준 달을 이번 달로 바꿀까요?"로 처리.
- 검토한 대안:
  - 서버 현재 날짜 기준: NFR-02 위반으로 기각
- 추가 고려: 파라미터를 바꿀 일이 생기면 `paramsVersion`도 응답에 넣는다.

### 비교는 같은 seed로 함께 계산한다
- 결정: `/compare`는 지금 계획과 비교 계획 1~3개를 같은 seed로 한 번에 계산한다. 계획 자체(`plans[]` = `name` + `adjustments`)를 본문으로 받는다.
- 이유: 시나리오별로 따로 계산해 캐시하면 차이에 난수 차이가 섞여, 작은 선택의 효과가 묻히거나 부풀려진다 (보고서 6.4 공통 난수).
- 대가: 캐시 재사용 불가. 3개 비교 약 0.3초라 3초 목표 안.
- 검토한 대안:
  - 시나리오별 캐시 재사용 (기존 명세): 공통 난수 원칙 위반으로 기각
  - 비교 시 반복 500회로 낮추기 (기존 명세): 2,000경로로도 시간 안에 들어와 불필요

### What-if 미리보기도 몬테카를로로 계산한다
- 결정: `/simulate/preview`는 확정 계산 1회가 아니라 같은 seed 2,000경로로 계산한다.
- 이유: 무작위성을 빼면 미리보기가 '계산기 결과'가 되어 서비스 핵심 메시지("실직·급전까지 넣으면")와 어긋난다.
- 대가: 계산량 증가. 엔진 단독 약 0.1초라 1초 목표 안.
- 검토한 대안:
  - 확정 계산 1회 (기존 명세): 빠르지만 핵심 메시지와 모순이라 기각

### 경로 수·기간은 보고서 기준을 유지한다
- 결정: 2,000경로 × 120개월 고정. 요청으로 바꿀 수 없다 (`iterations`·`years` 삭제).
- 이유: 보고서 7.10 수렴 검증에서 2,000경로의 흔들림은 0.94%p로, 가정 불확실성 범위(47~82%)보다 훨씬 작다. 파라미터 근거도 10년 범위.
- 검토한 대안:
  - 1만 경로 × 360개월 ("대용량" 연출): 보고서와 어긋나고 근거 범위 밖이라 기각. 대용량은 `/robust`(60회 × 2,000경로 = 12만 경로)를 큐·워커로 처리해 보여준다

### 필요 저축액은 격자 탐색으로 찾는다
- 결정: 0원 ~ 월 여유자금을 5만 원 간격으로 계산해 목표 확률(기본 70%)을 넘는 최소 금액.
- 이유: 납입을 늘리면 해지 위험 때문에 확률이 오히려 떨어질 수 있어 단조성이 보장되지 않는다 (보고서 6.4).
- 대가: 계산 횟수 증가 (격자 11개 약 1.1초).
- 검토한 대안:
  - 이분 탐색 (기존 명세): 단조성 가정이 깨져 기각
  - 기준 '중앙값이 목표에 닿는 금액'(= 확률 50%) (기존 명세): 보고서 기준(70%)과 달라 변경

### 비상금 먼저 모으기는 입력 필드로 둔다
- 결정: `savingPlan.emergencyFirstAmount`를 입력에 추가 (0/100/200/300/500만 원).
- 이유: 수정 제안서는 `adjustments`에만 두었는데, 그러면 사용자가 이걸 '지금 계획'으로 둘 수 없다. 보고서 6.1 ⑨("비상금 조건을 채웠으면")와도 맞춘다.
- 검토한 대안:
  - `adjustments`에만 둠 (수정 제안서): 지금 계획으로 설정 불가라 기각

### `/robust`는 비동기로 둔다
- 결정: 작업 id 발급(202) → 1초 폴링. 결과는 10분 보관. 동시 작업 상한 2개(`JOB4001`).
- 이유: node.js 기준 약 4.5초. 동기로 두면 요청 스레드를 오래 잡는다.
- 대가: 작업 결과를 서버 메모리에 두면 단일 인스턴스 전제가 붙는다 → [[../infra-queue-k6-aws-cicd/plan|인프라 작업]]에서 Redis 큐 + 워커로 해소.
- 재검토 조건: Java 이식 후 1~2초면 동기로 되돌릴지 판단.

### 엔진은 Java로 이식한다
- 결정: 파이썬 기준 구현(`kernel.py`)을 Spring Boot로 옮기고, 파이썬은 테스트 정답 파일 생성에만 쓴다 (보고서 4.1·8.3).
- 이유: 서버를 하나로 유지하고, 엔진 유지보수가 데이터분석 담당에게 묶이지 않게 한다.
- 검토한 대안:
  - 파이썬 엔진을 FastAPI로 띄우고 Spring이 호출: 이식·대조 작업이 사라지는 장점이 있지만, 서버 두 개·배포 복잡·유지보수 종속으로 보류
- 재검토 조건: 일정이 빠듯하면 다시 검토.

### decimal 연산은 쓰지 않는다
- 결정: 금액 반올림 규칙(원 단위 HALF_UP)과 확률 계산 방식만 명세에 고정한다. 엔진 내부는 double.
- 이유: 몬테카를로 전체를 BigDecimal로 돌리면 1초 목표를 못 맞춘다. 기간이 10년이라 오차 누적도 작고, 정답 파일 대조(확정 계산 오차 1e−6 이하)로 이미 검증한다.
- 검토한 대안:
  - 대출 상환·이자·확정 계산만 BigDecimal: 가능하지만 효용이 작아 보류

### 파라미터는 배포 전 고정 파일로 둔다
- 결정: `params.json` 읽기 전용. 실행 중 바뀌지 않는다.
- 이유: 파라미터가 매일 바뀌면 같은 입력의 결과가 날마다 달라진다(NFR-02 위반). 급전 확률은 특정 금리·물가 기준으로 보정된 값이라 자동 갱신하면 검증이 무효가 된다.
- 검토한 대안:
  - 한국은행 ECOS 매일 배치 수집 후 즉시 반영: 위 이유로 기각
  - 배치로 수집해 버전으로만 쌓고, 검증 후 `paramsVersion`을 올릴 때만 반영: 타당하지만 이번 범위 밖

### 입력 검사는 들어온 값만 본다 (2026-10-21, 팀 확인 필요)
- 결정: `/inputs/validate`는 빈 칸을 오류로 보지 않고, 들어온 값의 범위·형식과 여러 칸 규칙(INPUT4001 등)만 검사한다. 합계·경고는 필요한 값이 다 있을 때만 만들고, 없으면 `null` / 경고 없음. `step`은 선택이며 검사 범위에 영향이 없다.
- 필수 칸 확인은 두 곳에서 한다: 프론트는 필수 칸이 다 채워져야 '다음' 버튼을 켜고, 백엔드는 계산 API(`/simulate` 등) 직전에 전부 확인한다(`InputValidationService.checkRequired`).
- 이유:
  - 빈 칸 오류는 사용자가 입력하는 동안 바로 보여야 해서 프론트가 맡는 게 자연스럽다. 서버가 단계별로 필수 칸을 판단하면 화면 구성(어느 칸이 몇 번째 화면인지)을 서버가 알아야 해서 화면이 바뀔 때마다 서버도 고쳐야 한다.
  - 와이어프레임이 명세와 다르다(01-1에 나이·경력 칸 없음, 생활비는 선택 등). 단계별 필수 검사를 두면 화면이 확정될 때까지 서버 코드가 계속 흔들린다.
  - 서버 검사는 그대로 남긴다. API는 누구나 직접 호출할 수 있고, 합계·청년미래적금 자격 같은 계산은 백엔드 한 곳에서만 한다(보고서 4.3).
- 대가: 범위 규칙(나이 19~39 등)이 프론트와 서버 두 곳에 생긴다. 규칙은 노션 명세 한 곳에만 적고, 둘이 다르면 서버가 기준이다.
- 검토한 대안:
  - `step`까지 누적으로 필수 칸 검사 (10/8 명세): 화면 구성을 서버가 알아야 하고, 와이어프레임과 어긋나 기각
  - 서버 검사 없이 프론트만 검사: API 직접 호출·프론트 버그를 막지 못해 기각
- 남은 결정: 단계마다 `/inputs/validate`를 부를지, 마지막에 `/simulate`만 부를지는 프론트와 정한다. 어느 쪽이든 서버 코드는 같다.

| 월별 현금흐름 표 (기능명세 2.1.2) | 보고서 FR에 없음, 엔진 출력에 없음 |
